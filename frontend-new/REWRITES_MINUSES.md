# Минусы использования Rewrites для /uploads/*

## ⚠️ Основные минусы:

### 1. **Дополнительная нагрузка на сервер**
   - Каждый запрос к `/uploads/*` проходит через Next.js сервер
   - Next.js делает HTTP запрос к старому фронтенду
   - Удваивается нагрузка: Next.js → Старый фронтенд → Файл
   - Медленнее, чем прямая отдача файлов

### 2. **Зависимость от старого фронтенда**
   - Если старый фронтенд недоступен, статика не работает
   - Нужно поддерживать два сервера одновременно
   - Проблемы при деплое (старый фронтенд должен быть доступен)

### 3. **Проблемы с производительностью**
   - Нет кэширования на уровне Next.js (каждый запрос = новый HTTP запрос)
   - Медленнее, чем CDN или прямая отдача через веб-сервер
   - Больше задержка для пользователей

### 4. **Проблемы в production**
   - На Vercel/Netlify rewrites работают, но добавляют задержку
   - Нужен доступ к старому серверу из Next.js приложения
   - Могут быть проблемы с CORS, если домены разные

### 5. **Ограничения Next.js**
   - Rewrites не работают для статической генерации (SSG)
   - Могут быть проблемы с оптимизацией изображений Next.js
   - Не работает с `next/image` для внешних источников без настройки

### 6. **Сложность отладки**
   - Сложнее отследить проблемы (Next.js → Старый фронтенд)
   - Дополнительные логи и мониторинг
   - Проблемы с ошибками 404/500

## ✅ Когда использовать Rewrites:

- ✅ Локальная разработка (когда CDN недоступен)
- ✅ Временное решение при миграции
- ✅ Когда нет доступа к настройке веб-сервера
- ✅ Когда старый фронтенд всегда доступен

## 🎯 Рекомендации:

1. **Для локальной разработки** - используйте rewrites (как сейчас настроено)
2. **Для production** - используйте CDN (`site_cdnUrl` из настроек) или настройте веб-сервер
3. **Лучший вариант** - комбинация:
   - Development: rewrites
   - Production: CDN или веб-сервер

## 📝 Настройка:

Добавьте в `.env.local`:
```env
OLD_FRONTEND_URL=http://localhost
# или для production:
OLD_FRONTEND_URL=https://prostoj.store
```
